auroraADE architecture

Project boundaries and platform implementation notes.

This page separates the role of auroraADE from the technical contracts documented in the reachOS repository. It is a reference for project structure, boot, memory, devices and display—not a claim that the full desktop environment is already implemented.

\n

Names and responsibilities

These names describe related parts of the project, but they do not mean the same thing. In particular, the virtual hardware platform's CPU integration boundary and auroraADE's target architecture describe different layers.

Name Role What that means
reachOS Operating-system project The wider project in which the virtual platform and desktop environment sit.
Fabric Dessert Virtual hardware platform The board and hardware foundation documented in the reachOS repository, including CPU boundaries, physical memory, device bus, boot substrate and display path.
FRT64 CPU integration boundary The documented boundary is designed to accommodate ARM 32-bit, ARM 64-bit, x86 32-bit and x86 64-bit CPU integrations.
auroraADE Desktop environment direction ADE stands for Aesthetic Desktop Environment. auroraADE's target is x86_64; it should not be described as targeting every architecture supported at the broader platform boundary.

How to read the architecture notes

The technical sections below refer to components and contracts described in the current public reachOS source. They provide context for the environment auroraADE belongs to; they are not a claim that every platform component is an auroraADE user-facing feature.

Platform architecture

The reachOS README describes a separation between the browser-facing host shell and the Fabric Dessert platform runtime. The host provides integration with the browser; the platform code owns the virtual board and its subsystems.

Browser / host environment
└── Angular host shell (src/app/)
    └── Fabric Dessert runtime (src/fabric-dessert/)
        ├── Board and boot substrate
        ├── FRT64 CPU boundary
        ├── Physical address space and sparse RAM
        ├── Device bus, MMIO and IRQ routing
        └── Display device, framebuffer and renderer
Source area Documented responsibility
src/app/ Angular host shell and the bridge between the browser application and the platform runtime.
board/ Board configuration and boot ROM/reset-vector contract.
arch/frt64/ CPU-boundary types and execution integration points.
memory/ Physical address space, memory backing and memory-access context.
device/ Device interfaces and the bus used to manage MMIO windows and interrupt lines.
display/ Display device, framebuffer, system renderer, canvas backend and console font.

The platform is intended to keep its internal runtime separate from direct Angular and DOM dependencies. The browser integration is handled at the host boundary rather than being mixed into the platform's device and memory models.

Boot and CPU boundary

The documented reset path is a platform contract, not a generic description of every CPU's boot behavior.

  1. The board begins its reset sequence and resets the device bus while propagating the configured reset vector.
  2. The primary boot CPU enters the reset state, with its program counter set to the configured Fabric Dessert reset vector.
  3. Secondary CPUs are parked until future operating-system SMP bring-up.
  4. Instruction fetch crosses the CPU boundary into the physical address space and accesses the Boot ROM with execute permissions enforced.

The repository documents the Boot ROM and reset vector at 0x00000000 as the Fabric Dessert board contract. That address is not presented as an ISA-wide or Linux-specific rule.

FRT64 defines the CPU integration boundary. Its presence should not be read as a claim that a complete instruction set implementation for every listed architecture is already supplied by the same boundary module.

\n

Physical memory and devices

Memory model

The platform's physical address space uses 64-bit bigint addresses. Sparse physical backing is allocated in 64 KiB chunks, rather than eagerly allocating the entire configured RAM range.

Region mapping includes conflict checks and access-boundary validation. Memory-mapped device access is dispatched through the address-space/device model.

Device model

DeviceBus manages MMIO address windows, alignment, interrupt-vector assignments and device enumeration. Device interfaces provide a common boundary for controllers, timers, display devices and other peripherals.

These contracts describe how platform components connect; they do not, by themselves, define the user-facing behavior of an application or desktop shell.

\n

Display pipeline

The reachOS README documents a display path with explicit responsibilities for the virtual device, pixel storage, rendering coordination and browser-canvas presentation.

  1. Display device. Exposes control registers and a framebuffer memory aperture through MMIO. The documented register magic value is 0x53494446.
  2. Framebuffer. Uses a 1080 × 2424 pixel surface with RGBA8888 pixels, totalling 10,471,680 bytes of pixel storage.
  3. System renderer. Coordinates platform-side presentation and is documented as having no direct DOM or browser dependency.
  4. Canvas backend. Bridges the pixel buffer to the host canvas with a deterministic 1:1 coordinate mapping, without interpolation or layout-driven scaling.
  5. Console font. The documented default is font_sun_8x16, a 256-glyph, 4096-byte bitmap font for the bootloader and kernel console.

This is the documented platform display pipeline. It should not be mistaken for a screenshot of auroraADE or proof of a finished desktop session running on it.

Scope and current evidence

This page is based on the public reachOS README and the source areas linked above. It records the project separation and technical contracts documented there, rather than filling gaps with hypothetical product features.

The reviewed documentation does not establish the implementation status or behavior of an auroraADE desktop shell, window manager, panel or dock, file manager, launcher, or bundled application set. Those are intentionally not listed here as completed features. The x86_64 target is documented as a direction, not used as proof that every part of the desktop environment is complete.

As the implementation and its specifications become more explicit, this page can describe those details against their actual source files instead of relying on a generic list of desktop-environment features.
